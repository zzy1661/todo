## 0. 文档定位与阅读指引

### 0.1 本文是什么

本文是 **macOS 版**的产品需求文档。四份附件描述的是 **Windows 上已验证的现成产品**，它们是**事实基线**，不是 macOS 版的需求文档。本文做三件事：

1. 把基线里**必须逐条保持的行为契约**写成带编号的需求与业务规则（§8 FR-、§9 BR-）。
2. 把基线里**属于 Windows 实现细节、不得进入 FR 的取值**单独收进 §10「macOS 适配点」（ADP-）。
3. 把**材料未定义、不能自行拍板**的口径全部收进 §15（OP-），并给出默认建议与影响面。

### 0.2 三类内容的判定标准（写作纪律）

| 类别 | 判定标准 | 落在哪一节 | 能不能改 |
| --- | --- | --- | --- |
| 行为契约 | 用户可观察到的结果；换平台后必须一致 | §8 FR- / §9 BR- | 不能改；改动等同需求变更 |
| 实现细节 | 只对 Windows 成立的技术取值（安装器、路径、浏览器 channel、脚本语言） | §10 ADP- | 必须替换，且不构成需求变更 |
| 未知口径 | 材料未写、需要人拍板 | §15 OP- | 拍板前不得实现 |

`multica-pm-artifact-publish` 的默认落地是「Confluence 建 PRD 页 + JIRA 建 Story」。本工作区的 Confluence / JIRA 配置仍是模板占位值（`http://your-domain.atlassian.net/...`），且环境中不存在 `JIRA_USERNAME / JIRA_PASSWORD / CONFLUENCE_USER / CONFLUENCE_PASS` 任何凭据，**平台侧不可写入**。按该 skill 的 Workflow E（降级：PRD 全文进 Issue），本文以 Markdown 附件随 ZACHTD-2 交付。凭据与空间配置就绪后，可直接用本文正文执行 Workflow A，不需重写内容。

## 1. 一句话定义

在 macOS 上从零重建「日程待办 / Schedule Todo」：一个**纯本地、无账号、无云依赖**的桌面应用，提供日历、每日工作法、全部待办三个模块，**可观察行为与 Windows 基线逐条等价**，并以 macOS 原生产物（`.app` / `.dmg`）交付。

## 2. 背景与问题

### 2.1 现状

| 事实 | 说明 |
| --- | --- |
| 产品已存在且可用 | Windows 侧已交付并验证：三个模块、65 条方法库、右键菜单搬日期、双数据源（SQLite / localStorage） |
| 目标用户环境变化 | 需要在 macOS 上使用同一产品 |
| 代码不继承 | 原 `todo` 仓库代码全部废弃，从零重建（Leader 已定边界） |
| 材料只覆盖行为，不覆盖 macOS 壳层 | SPEC/PLAYBOOK/AGENTS/README 描述的是 Windows 实现；安装器、数据库路径、验证脚本、浏览器 channel 均为 Windows 取值 |

### 2.2 要解决的问题

| 编号 | 问题 | 后果（不做会怎样） |
| --- | --- | --- |
| P-01 | 需求侧没有 macOS 版范围定义，只有 Windows 事实基线 | 设计与开发各自发挥，行为漂移，无法判定「移植完成」 |
| P-02 | Windows 实现细节与需求混在一份材料里 | 照抄时会把 NSIS / `%APPDATA%` / `msedge` 当成需求，产出在 macOS 上直接不可用的方案 |
| P-03 | 行为契约（哈希推送、两表、迁移铁律、日期口径）分散在四份材料正文里 | 重建时被"顺手优化"掉，用户侧表现为「同一天推送变了」「升级后待办少了」 |
| P-04 | macOS 侧验证方案不存在（`.ps1` / UI Automation / `channel: 'msedge'` 全部不可用） | 交付时无法证明可用，只能口头声明 |
| P-05 | 65 条方法库正文不在本工作区材料内，仅提供了结构与统计口径 | 「65 条内容逐条保持」这一契约在验收时无对照物（见 RISK-01 / OP-01）。**已于 2026-11-01 由 OP-01 关闭：`methods.ts` 已随 Issue 交付** |

## 4. 用户角色与权限（U-）

| 编号 | 角色 | 描述 | 权限 |
| --- | --- | --- | --- |
| U-01 | 本机用户（唯一角色） | 在自己的 macOS 上使用应用的人；数据仅存在本机 | 全部功能；无分级、无审批、无共享 |

## 9. 业务规则（BR-）

> 本节是**不可协商**的行为契约。与 §10 冲突时以本节为准；与 Windows 实现取值冲突时以本节为准。

| 编号 | 规则 | 判定要点 | 关联 |
| --- | --- | --- | --- |
| BR-01 | **日期口径**：所有日期一律为 `YYYY-MM-DD` 字符串（本地时区语义），仅使用 dayjs 处理日期运算与格式化，不使用其他日期库，不把 `Date` 对象跨层传递 | 数据层、store、组件三处传参均为字符串 | INV-06 |
| BR-02 | **排序**：全量查询按 `date ASC → priority DESC → id DESC`；单日查询按 `priority DESC → id DESC` | 同优先级下新建条目在前 | — |
| BR-03 | **优先级**：`0 = 低`、`1 = 中`、`2 = 高`，数值越大越紧急；新建默认 `1`（中） | 取值为整数，不含其他枚举 | — |
| BR-04 | **完成率**：`round(已完成数 / 总数 × 100)%`；总数为 0 时**不显示**（不显示 0%） | 分母为该视图当前总条数（不是筛选后的条数） | — |
| BR-05 | **确定性推送**：以日期字符串为种子，使用 FNV-1a 哈希 + mulberry32 伪随机 + Fisher-Yates 全排列得到当天 65 条的固定顺序，取第 0 条为首推；「换一条」取 `(当前下标 + 1) % 65`。算法必须**逐字等价**（附录 A），保证同一日期在 Windows 与 macOS 上得到同一条 | 同日期不同机器/不同重启结果一致 | INV-03 |
| BR-06 | **推送落库**：日期为主键；首推写 `manual = false`，换一条写 `manual = true`；重复写入为覆盖更新 | 一日一行 | INV-04 |
| BR-07 | **两表固定**：待办表 `todos`、每日推送表 `daily_picks`。不新增第三张表、不合并、不改名、不把推送记录塞进待办表 | 表名与自增主键类型一致 | INV-04 |
| BR-08 | **迁移只增不改**：新增能力一律追加更高版本号的迁移；SQL 只允许 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`；**禁止** `DROP`、`ALTER`、`DELETE`、`UPDATE` 既有表结构与既有数据 | 迁移文件内检索无 `DROP` / `ALTER` | INV-05 |
| BR-09 | **改日期后必须重查当月**：任何改变待办日期的操作完成后，必须重新拉取当前月数据，否则日历圆点与统计会与列表不一致 | 移动今日/明日、编辑器改日期、复制到今日 | — |
| BR-10 | **新建后必须同步月数据**：新建待办后必须刷新当前月数据，让日历圆点立即出现 | 与 FR-CAL-04 联动 | — |
| BR-11 | **菜单不得出现自操作项**：今日条目不得出现「复制到今日」「移动到今日」；非今日条目不得出现「移动明日」以外的过去向操作 | 菜单项由日期分支生成，不是置灰 | FR-MENU-01 |
| BR-12 | **内容库契约**：方法总数 65；分类计数 思维 17 / 工作 17 / 汇报 12 / 沟通 7 / 效率 12；每条含 `id`（全局唯一 kebab-case）、`name`、`category`、`source`、`summary`、`steps`（每条 ≥ 2 条；真实分布 3–7，4 条超限条目见 §11.5 且判定合规）、`when`、`action`；`case` 为**可选**字段，取值 `practice` 或 `story`；当前 65 条全部带 `case`，其中 practice 18 / story 47；案例正文 126–240 字 | 数量与分布必须精确相等，不得"约等于" | INV-02 |
| BR-13 | **存储抽象**：store 只调用数据层导出的函数，不直接调用 SQL、不直接读写 localStorage、不判断运行环境 | 代码检索 store 目录无 `sqlite` / `localStorage` / `__TAURI` | INV-07 |
| BR-14 | **数据隔离与不碰真实数据**：E2E 只用浏览器 localStorage；桌面版验证优先只读交互，若必须造数据，验证后逐条删除并比对条数、id、日期、完成态、标题确认还原 | 验证前后 `todos` 内容一致 | — |
| BR-15 | **技术克制**：不引入状态管理库（Pinia / Vuex）、不引入 UI 组件库、不引入路由库、不引入第二套日期库；样式手写 + CSS 变量；界面**全中文**；**浅色单一主题** | `package.json` 依赖清单可审 | — |
| BR-16 | **输入上限**：待办标题 ≤ 100 字，备注 ≤ 500 字，均为硬限制（输入即截断/阻止） | 与 FR-EDT-02 一致 | — |
| BR-17 | **纯本地**：启动不读网络、不登录、不上报；所有数据只存本机 | 断网可完整使用 | FR-DB-11 |
| BR-18 | **单个用户数据源**：同一台机器上只有一个数据源（一个 SQLite 文件 / 一份 localStorage），不做多配置档案、不做工作区切换 | — | — |
| BR-19 | **E2E 稳定性纪律**：日历日期格按日期数字精确匹配并排除补位格；用例不得依赖运行当天日期；产物留存目录与测试输出目录分离 | 换日期仍全绿 | FR-QA-04 FR-QA-06 |
| BR-20 | **菜单关闭条件五项全开**：点击外部、`Esc`、窗口失焦、窗口尺寸变化、页面滚动 | 五项逐一可复现 | FR-MENU-08 |
| BR-21 | **模块状态互不污染**：三个模块各自持有自己的界面状态（筛选、查看日期等），切换模块不重置彼此已确认的数据视图（唯一例外：当日面板切换日期时筛选重置，见 FR-DAY-04） | 切模块再切回，筛选不丢 | — |
| BR-22 | **语言与术语一致**：界面文案与基线完全一致，包括 `日程待办`、`Schedule Todo`、`数据本地存储`、`今日工作法`、`这一天还没有待办`、`没有符合筛选的待办`、`复制到今日`、`移动到今日`、`移动明日`、`方法库预览`、`已手动刷新`、`今日推送` | 文案不得"优化"或改写 | — |
| BR-23 | **空白与全量数据的可读性**：任何列表在 0 条、1 条、4 条以上（触发 `+` 标记）三种规模下都不得出现布局塌陷或裁切 | 三种规模逐一截图核对 | — |

## 附录 A · 确定性推送参考实现（用于 AC-24 比对）

以下为**行为契约级**参考实现，macOS 版可改变文件位置与写法，但**计算过程与结果必须逐字等价**。

```ts
// 稳定哈希（FNV-1a）
function hashCode(str: string): number {
  let h = 2166136261;
  for (let i = 0; i < str.length; i++) {
    h ^= str.charCodeAt(i);
    h = Math.imul(h, 16777619);
  }
  return Math.abs(h);
}

// 可复现伪随机（mulberry32）
function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// 某日期的确定性全排列（Fisher-Yates）
function permutationFor(date: string, ids: string[]): string[] {
  const out = [...ids];
  const rand = mulberry32(hashCode(date));
  for (let i = out.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1));
    [out[i], out[j]] = [out[j], out[i]];
  }
  return out;
}
```

比对口径（QA 执行）：

1. 从内容库取出 65 个 `id`，保持**内容库数组原始顺序**作为输入（顺序不同则排列不同）。
2. 对抽样日期 `d` 计算 `permutationFor(d, ids)`。
3. 断言 `permutationFor(d, ids)[0]` 等于数据库中该日 `method_id`（当 `manual = 0`）。
4. 对 `manual = 1` 的日期，断言数据库中的 `method_id` 出现在 `permutationFor(d, ids)` 中，且其下标 = 首推下标 + 1（模 65）。
5. 同一日期重复计算 3 次结果一致；更换机器/重启后结果一致。

#### D.2.1 CFL-07 裁定依据

**冲突事实**（对 `methods.ts` 独立求值所得，非引用他人结论）：

| 项 | 实测 | 说明 |
| --- | --- | --- |
| 总条数 | 65 | 与材料一致 |
| `steps` 分布 | 3 条 × 6、4 条 × 55、5 条 × 3、7 条 × 1 | 合计 65；**观测区间 3–7，不存在 2 条条目** |
| 超限条目 | `gtd` 5 / `smart-goal` 5 / `5w2h` 7 / `rice-scoring` 5 | 共 4 条 |

**裁定逻辑**：

1. 本项目的等价对象是 **Windows 基线实际交付的那 65 条数据**，不是 SPEC 里那条内容创作规范。规范与交付物冲突时，以交付物为准。
2. SPEC 的「2–4 条」描述的是"新增方法时怎么写"，属于**写作建议**，不构成对既有数据的验收条件；把它当硬断言会在**正确数据上误报失败**（`check-cases.mjs` 直接红），导致 G2 冤判。
3. 因此断言改为 **`steps ≥ 2`**（防止空步骤），并记录真实分布作为回归基线；4 条超限条目在此基线下**恒为通过**。
4. 数据原样搬运，一条不改文案；不得为凑规范把这 4 条压到 4 条以内——那才是破坏行为等价。
5. 设计侧必须按真实数据评估卡片高度：`5w2h`（7 步）与 `rice-scoring`（正文总长最大）在 1100×720 窗口下必然超出可用高度，二者固定为「内部滚动 + 底部渐隐」路径的 E2E 夹具。

> 一句话：**`steps` 上「行为等价」的判定标准是数据，不是规范。** 规范可以留作后续新增内容的建议，但不能用来给既有数据判错。
